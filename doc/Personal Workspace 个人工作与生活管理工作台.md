# 1. 项目概述

## 1.1 产品背景

日常工作和生活中，待办、日程、提醒、日报等信息经常分散在不同工具中。用户需要在多个应用之间切换，信息之间缺少关联，记录和执行也容易断开。

本产品希望将这些常用能力整合到一个轻量的本地工作台中，让用户每天打开应用，就能清楚知道：

-   今天有哪些安排？
-   当前最应该做什么？
-   哪些事情已经完成，哪些已经逾期？
-   临时想到的事情应该放在哪里？
-   今天做了什么，之后如何回顾？

## 1.2 产品定位

**一个以「今天」为中心、以时间为线索、覆盖工作与生活的个人管理工具。**

核心原则：

1.  今天优先：默认进入「今天」，不让用户先思考应该打开哪个模块。
2.  信息有关联：待办、日程、提醒、每日总结之间可以自然关联。
3.  快速捕获：先记录，再整理，不要求创建时填写完整信息。
4.  历史可追溯：完成事项、每日总结和提醒历史不因状态变化而丢失。
5.  本地优先：数据保存在用户自己的电脑，不依赖服务器和账号。
6.  轻量易用：界面简洁，操作直接，不做复杂项目管理系统。

## 1.3 产品目标

-   用一个入口管理工作、生活、学习中的日常事项。
-   降低记录和整理信息的成本。
-   让待办与日程、提醒和每日总结形成闭环。
-   让用户能够方便地回顾某一天或某一段时间。
-   在本地安全保存数据，并提供备份与恢复能力。

## 1.4 非目标

V1 不追求以下能力：

-   多用户、团队协作、组织权限。
-   云端账号体系和多设备实时同步。
-   公网部署与远程访问（只监听本机回环地址）。
-   移动端适配。
-   复杂甘特图、资源排期和企业级项目管理。
-   完整工时统计、考勤或计费系统。
-   在线文档协作。
-   AI 自动规划作为核心依赖。

# 2. 用户与核心使用场景

## 2.1 目标用户

主要面向希望在个人电脑上统一管理工作与生活事项的个人用户。用户不需要学习复杂方法论，也不需要配置大量规则。

## 2.2 核心场景

### 场景 A：开始一天

打开应用后进入「今天」，查看当天日程、待办、提醒、重要日子和昨晚日报里的明日计划，明确当天安排。

### 场景 B：临时想到一件事

快速创建只输入标题，默认不设日期，进入待安排池，之后想做了再安排。

### 场景 C：把待办安排到某一天

创建待办，设置计划执行日期、截止日期和提醒。

### 场景 D：完成一项工作

勾选完成后，系统记录完成时间，保留历史。

### 场景 E：晚上写日报

下班前打开「每日总结」，写「今日工作」（实际做的，可能和计划不符）和「明日计划」（只是打算）。今日工作逐行自动记入当日完成数据；明日计划第二天早上自动出现在「今天」页，到时再决定转不转待办。写完一键复制交日报。

### 场景 F：计划被打乱

明天临时有事，昨晚的计划没做。未完成的条目不会消失，自动顺延并标记「遗留 N 天」，直到完成或主动放弃。

### 场景 G：处理提醒

提醒到期后通过页面内通知提示用户，可选择打开事项、稍后提醒或完成相关事项。

# 4. 核心功能需求

## 4.1 今天

### 页面目标

让用户在一个页面中掌握今天需要关注的全部信息。

### 页面内容

1.  日期与简短问候。
2.  今日概览：待办总数、已完成、剩余、逾期、日程数量。
3.  重要提醒：已到期或即将触发的提醒。
4.  重要日子：当天恰逢生日/纪念日时显示横幅提醒。
5.  今日工作计划（来自昨天日报的「明日计划」）：昨天写的计划条目，逐条「转为待办」或「忽略」（忽略后可撤销）；计划本身只展示，不计入待办和完成统计。
6.  今日时间安排：按时间排序展示日程。
7.  今日待办：含顺延的遗留条目（标记「遗留 N 天」）。
8.  今日待办卡片底部的快速添加输入框：回车即建一条计划日期为今天的待办并直接进列表，不打开快速创建弹窗（弹窗留给需要选类型/日期/分类的场景）。
9.  已完成事项：默认折叠，可展开查看。

### 交互规则

-   计划执行日期为今天的待办进入今天列表。
-   今天页的快速添加只填标题：日期固定今天，分类/优先级用默认值，保存后到待办页再调整。
-   没有计划日期的待办不自动进入今天（进入待安排池）。
-   计划日期已过但未完成的待办自动顺延，带「遗留 N 天」标记，直到完成或删除。
-   已完成事项保留在历史中，不直接删除。
-   点击待办打开详情。

## 4.2 收集箱

### 页面目标

快速收纳尚未分类、尚未安排或暂时不确定类型的信息。

### 业务规则

-   收集箱内容不自动计入今日待办统计。
-   收集项可以保持信息不完整。
-   整理为待办时保留原始创建时间和必要内容。
-   收集箱不应变成另一个复杂任务列表。

## 4.3 待办

### 页面目标

管理所有需要用户主动完成的事情，并作为所有待办的总账页（今天、明天、待安排、遗留、已完成都在这里可见）。

### 字段建议

  字段                    说明
  ----------------------- --------------------------------
  Id                      唯一标识
  Title                   标题，必填
  Status                  未开始、进行中、已完成、已取消
  Priority                低、普通、高、紧急
  CategoryId              主分类
  PlannedDate             计划执行日期
  DueDate                 截止日期
  EstimatedMinutes        预计耗时，可选
  CompletedAt             完成时间
  SourceType              来源：手动 / 明日计划 / 收集箱 / 日报
  CreatedAt / UpdatedAt   创建和更新时间
  IsDeleted               软删除标记

### 待安排池

-   快速创建默认不设置日期，新建待办进入「待安排」池。
-   待安排的待办不催促、不进入今天。
-   想做的时候一键「安排到今天」。

### 顺延规则

-   计划日期已过但未完成的待办自动顺延，带「遗留 N 天」标记。
-   遗留条目一直保留，直到完成或删除（删除 = 主动放弃）。
-   遗留不改变任务状态字段，仅是展示层标记。

### 标签与分类

-   每个待办一个主分类；分类有颜色（工作=蓝、生活=绿、学习=紫，可自定义）。
-   每个待办多个标签；标签颜色从 8 色验证色板按创建顺序自动分配，同名标签全局同色。
-   分类在详情面板用下拉指派；标签在详情面板用勾选器指派。
-   分类徽章用中性样式，标签用彩色样式，视觉上区分两个概念。
-   待办页顶部有「分类 / 标签」筛选，可组合；点列表行上的分类徽章或标签，直接跳到待办页并按它筛选。
-   标签管理页显示每个标签的未完成条数，点标签也能直接查看相关待办。

### 格式与展示

-   待办列表按「今天 / 明天 / 待安排 / 已完成」分组。
-   组内按时间倒序：未完成的先按优先级、同优先级新创建的排在前面；已完成按完成时间倒序，最新的在最上面。
-   已完成行的完成时间显示完整年月日（如「2026年11月5日 16:14 完成」），跨天后仍能看出是哪一天完成的。
-   筛选标签页带实时计数。

### 来源标记与批量清理

-   由「明日计划」转出的待办带「工作计划」徽章（强调色描边），一眼能认出这是计划来的、不是当天临时加的。
-   收集箱转出的待办带「收集箱」徽章；手动新建的不带来源徽章，避免列表噪音。
-   待办页右上「多选」进入多选模式：行首出现勾选框，点击行即选中；工具条提供「全选 / 清空 / 删除选中（N）/ 退出多选」。
-   批量删除走软删除（`is_deleted=1`），关联提醒一并失效，完成历史按规则保留；删除前二次确认。

## 4.6 每日总结（原「每日记录」，重构）

### 页面目标

每晚下班前写日报，结构固定为两段：

``` text
今日工作
- xxx
- xxx

明日计划
- xxx
- xxx
```

### 核心语义（重要）

-   **今日工作写实际做的**：可能和昨晚的计划完全不符，可能全是临时插入的事，这是正常的。
-   **明日计划只是打算**：第二天实际做什么以实际为准，不需要回头对账。
-   **日报是叙述，待办是事实**：系统不做「计划 vs 实际」的达成率统计。
-   **两者互不依赖**：写日报不要求先有待办；待办勾选不要求写日报。

### 格式规则

-   每行只认两种格式：`- 内容` 或 `1. 内容`（数字编号）。
-   格式不正确的行实时标红提示：「格式不正确：第 N 行『xxx』· 请改成 - 内容 或 1. 内容」。
-   空行允许（分隔用）。

### 自动行为

-   **今日工作 → 完成数据**：写完失焦后逐行自动记入当日完成数据；与现有待办同名的自动勾选该待办，没有对应待办的自动新建已完成记录（来源标记「日报」）。补写往日日报时，完成时间记到那一天的中午，只计入那一天的完成统计，不出现在今天的已完成列表；**未来日期只保存文字，不生成完成记录**。
-   **按天各记一条**：去重只比较「同一天 + 标题」。以前某天完成过同一件事，今天日报再写一遍，仍算今天的完成。
-   **日报同步**：日报里删掉一行，同步移出当天由日报生成的完成记录；改写一行，同步改名并保留原完成时间。手动勾选完成的任务不受影响；当天由日报生成、被用户手动删除的记录不会被再次重建（同步删除记录除外，重新写回该行会重新生成）。
-   **明日计划 → 次日浮现**：今晚写的明日计划，明天早上自动出现在「今天」页的「今日工作计划」卡片，逐条决定「转为待办」或「忽略」。
-   **未完成顺延**：转成待办后没做完的，自动顺延并标记遗留，直到完成或删除。
-   除上述两个自动行为外，系统不修改、不解读日报文字。

### 日期切换

-   顶部日期按钮点开月历，直接选任意一天；「‹ ›」逐日翻；不在今天时出现「今天」按钮，一键回到今天。
-   页面一直开着跨过零点：如果当前看的本来就是「今天」，下一次进入页面/窗口重新获得焦点时自动切到新的今天；手动翻到往日或未来时保持不动。
-   月历里写过「今日工作」的日期带圆点，一眼看出哪些天写了日报。
-   切换日期前会先保存当前这天的内容；有格式不正确的行时阻止切换并提示，不会静默丢内容。

### 复制日报

按「今日工作 + 明日计划」格式整份复制到剪贴板，用于粘贴到公司 IM 或邮件。

# 5. 核心业务规则

## 5.1 待办日期规则

-   PlannedDate：计划在哪一天执行。
-   DueDate：最晚应在哪一天完成。
-   两者含义不同，不应合并。
-   没有 PlannedDate 的待办进入待安排池。
-   PlannedDate 已过但未完成的待办自动顺延，标记遗留。
-   未完成且当前日期超过 DueDate 时显示为逾期。
-   完成事项保留 CompletedAt 和历史记录。

## 5.2 完成历史与日报

-   完成待办时写入完成时间。
-   完成数据的来源有两个：白天的勾选 + 晚上日报「今日工作」的逐行记入，按「同一天 + 标题」去重合并（不同日期写过同一件事各记各的）。
-   日报文字改动会同步当天由日报生成的完成记录：删掉的行移出，改名的同步改名；手动勾选完成的任务不受影响。
-   来源写在任务上（completed_via：手动 / 日报），两者都计入完成统计，但可区分：已完成列表提供「全部 / 勾选完成 / 日报记录」筛选，今日完成显示为「勾选 A · 日报 B」。
-   「明日计划」不计入待办与完成统计，只有用户显式转为待办后才参与。
-   日报文字本身不参与工作量统计；统计只认结构化事实（勾选、日程、提醒触发）。
-   「日报连续天数」统计的是填写行为（习惯指标），不是工作量。

## 5.3 明日计划生命周期

-   写入时：纯文字，不产生任何待办，无需确认。
-   次日：整组自动出现在「今天」页，逐条「转为待办」或「忽略」，可全部转为待办。
-   转成待办后：进入待办体系，未完成自动顺延。
-   忽略后：标记「已忽略」留在卡片上，可点「撤销」恢复为待处理；不生成待办。
-   不转不忽略：保留在那天的日报原文里，可随时翻回查看或补转。

## 5.5 删除策略

（与 V1.0 一致；补充：删除分类后关联事项变为未分类，事项上的该分类徽章同步移除）

-   待办行悬停右侧出现删除按钮，未完成和已完成的条目都可以删；删除为软删除，关联提醒一并失效。
-   待办页还可进入「多选」批量删除；删除属于用户决定，当天由日报生成、被删除的同名条目不会被日报再次重建。

## 5.6 时间与日期存储

-   有具体时刻的字段统一按 UTC 时间戳存储，展示转换为本地时区。
-   纯日期字段使用 ISO 日期语义存储，不做时区换算。
-   全天日程按本地日期处理。

# 8. 技术实现方案

## 8.1 技术选型

  层面        技术                          说明
  ----------- ----------------------------- ----------------------------------------------
  运行时      Python 3.10+                  本地运行，无外部服务依赖
  Web 框架    FastAPI                       本地 HTTP 服务，监听 127.0.0.1
  前端        原生 HTML/CSS/JS              静态页面由后端提供；原型前端代码直接复用
  样式        Tailwind（构建期）            设计语言对齐 AISessionManager；CSS 变量主题
  图标        Lucide                        与原型一致
  数据库      SQLite（Python 内置 sqlite3）  本地单机存储
  通知        页面内通知 + Notification API 应用运行期间有效
  日志        logging 按天滚动              本地日志，保留最近 15 天
  配置        JSON                          本地用户配置
  打包        PyInstaller（可选）           后续按需提供单文件可执行版

明确不使用：云端服务、账号体系、多设备同步、消息队列、微服务。

参考实现模式：AISessionManager（本地 Python 服务 + 浏览器访问 + Tailwind Web UI）。

## 8.2 架构原则

简单三层，不做过度抽象：

``` text
webui/        静态页面与前端脚本（HTML/CSS/JS，原型代码迁移）
server/       FastAPI 路由：页面、静态资源、JSON API
core/         业务逻辑：待办、日程、提醒、日报、统计
storage/      SQLite 访问、迁移、备份恢复
providers/    预留：接入外部 AI 工具会话等
```

依赖方向：webui → server → core → storage。前端只通过 JSON API 读写，不直接碰数据库。

## 8.4 前后端约定

-   前端为无构建步骤的原生 JS 单页应用；所有写操作走 JSON API。
-   API 按资源划分：/api/todos、/api/events、/api/reminders、/api/journal、/api/special-days、/api/stats。
-   服务端只监听 127.0.0.1；启动后自动打开浏览器（可配置）。
-   端口冲突时自动顺延并在控制台输出实际地址。

## 8.5 数据访问

-   使用 Python 内置 sqlite3，开启 WAL 模式与外键约束。
-   所有写操作走统一的事务封装。
-   数据库结构用版本号迁移表（user_version）管理。
-   查询按需分页，避免一次性加载大量历史数据。

## 8.6 主题实现

-   CSS 变量定义色板（RGB 通道形式），`html.dark` 切换深色档。
-   主题选择存 localStorage，默认跟随系统 `prefers-color-scheme`。

# 9. 数据库设计建议

## 9.1 核心表

  表名                 用途
  -------------------- --------------------------------------
  sys_category         分类（含颜色）
  sys_tag              标签（含颜色序号）
  sys_item_tag         事项与标签关联
  biz_task             待办（含 source_type 来源标记）
  biz_calendar_event   日程
  biz_reminder         提醒
  biz_journal          每日总结（today_text / plan_text 分字段）
  biz_special_day      重要日子（name、type、date、yearly）
  biz_task_history     待办状态与重要变更历史
  sys_setting          用户设置
  schema_version       数据库结构版本

## 9.2 关键字段说明

-   biz_task.source_type：manual / quick / journal / inbox，用于追溯待办来源。
-   biz_journal：today_text 与 plan_text 分字段存储；逐行记入的完成数据写入 biz_task（source=journal），不在日报表中冗余。
-   biz_special_day.yearly：是否每年重复；倒计时按次年滚动计算。
-   明日计划的转换状态（已转/已忽略）按 journal 日期 + 行序号存储，或在转换生成待办时记录来源行，二选一在开发期定稿。

## 9.3 索引建议

-   biz_task：PlannedDate、Status、CategoryId、IsDeleted。
-   biz_calendar_event：StartAt、IsDeleted。
-   biz_reminder：TriggerAt、Status。
-   biz_journal：JournalDate 唯一索引。
-   biz_special_day：NextDate。

# 10. 提醒与通知

## 10.1 运行期模型

-   应用进程运行期间，由后端调度线程每分钟检查到期提醒。
-   到期后：写入提醒状态，并通过前端轮询 / SSE 推送到页面，展示页面内通知；若浏览器已授权 Notification API 则同时发系统通知。
-   应用启动时补查错过的提醒（上次运行期间到期的标记为「错过」并提示）。

## 10.2 明确的限制

-   进程退出后提醒不会触发（与 V1.0 结论一致，如实在文档与 UI 中告知用户）。
-   系统级提醒（计划任务、常驻托盘）列入后续版本评估。

-   列表分页；统计查询走索引。

-   日志避免记录用户敏感内容。
-   应用异常退出后，下次启动可恢复正常（WAL + 迁移校验）。

# 14. 核心验收用例

## 用例 1：快速创建与待安排

1.  快速创建只输入标题，不选日期。
2.  保存后出现在「待安排」池，不出现在今天。
3.  在待办页点「安排到今天」，出现在今天列表。

## 用例 2：创建待办并完成

1.  创建待办，计划日期设为明天。
2.  保存后不出现在今天列表。
3.  明天进入今天页应能看到该待办。
4.  完成后记录完成时间，进入完成统计与趋势。

## 用例 3：写日报

1.  在每日总结页输入一行无格式文字。
2.  出现红色提示「格式不正确」，要求改为 - xxx 或 1. xxx。
3.  修正后提示消失。
4.  写「明日计划」若干行，无任何按钮需要点击。
5.  次日打开「今天」，昨晚计划出现在「今日工作计划」卡片。
6.  逐条转为待办后进入今日待办；未转的保持在日报原文中。

## 用例 4：日报自动记完成

1.  白天勾选完成的待办，出现在完成统计。
2.  晚上日报「今日工作」写入与待办同名的一行，失焦后该待办自动勾选。
3.  写入一行不存在的新事项，失焦后自动新建一条已完成记录（来源：日报）。
4.  工作台「今日完成」数量与上述一致。

## 用例 5：计划顺延

1.  昨晚日报明日计划 5 条，全部转为待办。
2.  今天只完成 2 条。
3.  明天打开今天页，剩余 3 条仍在并标记「遗留 1 天」。
4.  大后天仍未处理，标记变「遗留 3 天」，持续可见。

## 用例 6：重要日子

1.  添加「妈妈的生日」，日期为明年 5 月 20 日，类型生日。
2.  重要日子页显示「每年 5月20日 · 还有 N 天」。
3.  当天打开「今天」页，顶部出现横幅提醒。
4.  可一键「记个待办」。

## 用例 7：备份恢复

1.  创建若干数据，执行备份。
2.  修改部分数据后从备份恢复。
3.  验证恢复结果一致，恢复前自动生成当前数据的备份。

# 15. 原型评审结论（V1.1 已归档）

第一版交互原型经多轮评审，以下结论已全部实现于原型并写回本文档：

1.  「每日记录」重构为「每日总结」：固定「今日工作 + 明日计划」两段结构，逐行格式校验（只认 `- xxx` 与 `1. xxx`）。
2.  今日工作失焦后逐行自动记入当日完成数据；与待办同名的自动勾选。
3.  明日计划生命周期：写时纯记录 → 次日自动浮现于今天页 → 逐条转待办/忽略 → 未完成自动顺延（遗留标记）。
4.  快速创建默认不设日期，待安排池承接；顺延机制覆盖所有未完成待办。
5.  「每日记录」更名「每日总结」；日报文字不参与工作量统计，只统计结构化事实；日报连续天数作为习惯指标。
6.  重要日子：独立页面 + 倒计时 + 今天页横幅 + 工作台。
7.  时间轴、工作台由 P1 转正。
8.  分类有颜色、标签有 8 色板配色并在待办行显示；详情面板支持分类下拉与标签勾选编辑。
9.  提供浅色/深色/跟随系统三态主题。

**产品成功的关键不是功能数量，而是用户每天打开它时，能否自然地完成记录、安排、执行和回顾。**

# 16. 给 AI 编码工具的开发约束

后续使用 AI 编码工具开发时，建议将以下约束作为项目级开发说明：

1.  严格按照本文档的产品边界和业务规则实现。
2.  技术栈：Python + FastAPI + SQLite + 原生前端；不引入 React/Vue 等前端框架，不引入除 FastAPI 外的 Web 框架。
3.  服务只监听 127.0.0.1，不做公网部署，不引入账号与认证。
4.  数据库只用 SQLite（内置 sqlite3），不用其他数据库。
5.  前端代码从原型 `个人工作台-交互原型.html` 迁移，保持设计语言与交互不变。
6.  日报语义红线：今日工作写实际做的，不与计划对比统计；明日计划转待办必须是用户显式操作（或次日浮现后的显式确认），不得在写入时静默生成待办。
7.  完成数据按标题去重合并：勾选与日报两个来源不能产生重复记录。
8.  所有日期规则必须区分计划日期、截止日期和具体时间。
9.  待办与日程保持不同实体和不同语义。
10. 完成历史必须保留，不能覆盖丢失。
11. 每日总结的今日工作/明日计划分字段存储，自动汇总类内容不得写入这两个字段。
12. 未完成待办自动顺延是展示层行为，不得修改任务的计划日期字段。
13. 提醒必须考虑进程退出、睡眠唤醒和启动补查，并如实告知用户限制。
14. SQLite 必须有版本迁移和备份恢复方案。
15. UI 保持简洁、留白、克制，不做成传统后台管理系统。
16. 每个阶段完成后更新文档、测试和变更记录。
